# Awesome Docs Skill

这个 skill 把工程文档需求变成写作步骤：先定位资料、选择深度，再组织章节或记录、检查推导与证据。它维护文档，不修改项目业务实现。

## 通用写作与交互图解

核心写作流程见 [technical-writing.md](references/technical-writing.md)，把 Google、Microsoft 和中文技术文档指南落实为检查动作、修改方法及正反例，而非只列写作原则。涉及公式和图示时再读 [interactive-illustrations.md](references/interactive-illustrations.md)，覆盖图内外 LaTeX、参考系、重点高亮、3D/2D 选择和离线网页验证。规则同样适用于 HTML 正文。本技能独立完成写作和审稿；`shuorenhua` 可用时按需增强润色，缺失则跳过增强，不触发安装。视频技能独立负责分镜与成片，复杂内容组织可按需参考本技能，双方不互为必需依赖。

## 文档分类与路径

默认使用目标项目的 `docs/`；用户指定路径和仓库已有约定优先。目录按需创建，不为一条待办建立整套空目录。

| 目录 | 用途 |
|---|---|
| `architecture/` | 当前系统结构、职责与数据流；`adr/` 保存架构决策 |
| `books/<topic>/` | 按章节组织的技术书，以 `README.md` 为唯一阅读入口 |
| `reference/` | API、协议、字段、配置、错误码等可直接查询的定义 |
| `plan/` | 某项改动的实施步骤、验证和回滚方案 |
| `roadmap/` | 阶段目标、里程碑、依赖和验收证据 |
| `todo/` | 持续更新的动作、想法、风险和未决问题 |
| `experiment/` | 有日期、数据来源和复现方法的实验记录 |
| `knowhow/` | 可复用的解释、排障经验与操作方法 |
| `常用命令.txt` | 用户要求保存的单行命令 |

## 具体怎么执行

主流程是：**定位目标 → 判断类型和读者 → 核对资料 → 设计结构 → 按类型写作 → 验证并修正 → 交付**。每一步写明继续之前应得到什么，发现缺口后返回哪一步；小更新不额外生成流程文档。

### 通用写作：逐项检查，发现缺口就回到对应步骤

| 环节 | AI 要具体做什么 |
|---|---|
| 读者与范围 | 把“介绍功能”改成读者要回答的问题，为每个核心问题指定正文位置 |
| 事实与术语 | 核对来源和版本，区分实现、推导、实测及提案；确认同一对象后才统一叫法 |
| 阅读顺序 | 写出每节依赖和结果，把必要定义前移，不照抄源码或材料顺序 |
| 开头与标题 | 只看目录查找答案；“相关说明”等模糊标题改为具体对象或任务 |
| 段落与句子 | 检查中心意思、执行者、条件、输入输出和因果依据；缺步骤先补证据 |
| 操作步骤 | 前提放在动作前，写清操作位置、预期观察和异常分支，区分受理与完成 |
| 比较与计算 | 对齐比较维度；说明取样、变换、聚合顺序、阈值来源并复算例子 |
| 修稿与验收 | 先修影响操作和结论的缺陷，再润色；分别报告静态检查、复算和实际渲染检查 |

例如“平均偏差”需要说明是先取绝对值再平均，还是先平均再取绝对值；“成功后继续”需要说明成功对应哪个状态。指南给出改写示例和失败后的修正位置。公式使用 LaTeX，数量与字幕优先用阿拉伯数字，保留“三维”等自然术语。小改动只检查受影响内容。

### Architecture：先选深度，再写对应内容

| 深度 | 写到哪里 | 何时停止 |
|---|---|---|
| L1 系统边界 | 使用者、外部系统、输入输出、范围 | 不展开内部进程、类或函数 |
| L2 运行单元 | 进程、服务、任务、存储及相互交换 | 不深入各单元内部模块 |
| L3 组件职责 | 某运行单元内的职责、契约、状态归属与流程 | 不罗列所有类和辅助函数 |
| L4 局部机制 | 一个算法、状态迁移或异常路径，含正常/边界案例 | 不扩展到无关实现 |

这四档是 skill 的写作层次，不是架构成熟度。每档提供资料检查顺序、责任表/图的构造步骤和验收条件。部署与时序是按问题增加的视图；源码中的模块不等于线上独立服务。

### Books：按章节推导，不把材料直接拼起来

1. 从读者最终要解答的问题倒推前置知识，建立章节依赖和每章输入、输出。
2. 在一个固定文件中建立全局符号表、缩略语表和约定，解决原材料中的同名异义。
3. 按真实问题、简单办法及局限、所需概念、推导、验证、下一问题展开章节。
4. 每个推导从已知量和假设开始：解释起始关系，逐步代数变形，说明每一步理由，再做数值、量纲和边界检查。
5. 公式用 LaTeX，复用公式有稳定引用；公式附近解释符号，定义与全局表一致。
6. 对高中基础读者，在首次使用导数、矩阵、Jacobian 等之前补具体小例，不用“跳过这一节”替代必需知识。
7. 新增或修改章节后，检查前置知识、全书符号、图注、公式引用和导出路径。

### 其它记录：写明操作与分支

- **experiment**：确认已有结果 → 冻结比较单位与筛选/配对规则 → 定义指标和分母 → 复算 → 写结论及边界。失败样本和重复会话有明确处理。
- **knowhow**：先选解释、排障或操作模式；排障步骤写明检查项、预期观察、下一分支、停止/恢复条件。
- **reference**：沿定义、校验、消费逻辑核对字段和版本，不把示例值猜成默认值。
- **plan / roadmap / todo**：分别写执行步骤、可验收结果、最小下一动作；不把“记录下来”写成“已经完成”。

## 命名与维护

- 实验、专题记录和实施计划默认用 `YYYYMMDD_主题.md`；同一计划推进时更新原文件。
- 架构现状、接口参考、roadmap、todo 使用稳定主题文件名；已有带日期的文件继续维护，不每天新建一份。
- 书籍使用 `books/<topic>/README.md`、`00_导读与符号.md`、`01_主题.md` 和 `figures/`。合卷是生成副本，不另设一份可编辑正文。
- ADR 默认用 `architecture/adr/YYYYMMDD_决策.md`；仓库已有编号规则时沿用。决策变化要保留被替代记录与链接。
- CSV、JSON、YAML 等参考资料保留原格式，不为了统一文档而强制改成 Markdown。
- 文档迁移后检查内部链接、反向引用、图片、构建脚本和导出路径。文档更新本身不触发提交、推送或发布。

写作先完成内容核对，再进行可跳过的语言润色。技术书按读者基础补齐符号、单位、假设和中间推导；公式、历史数据、协议字段及命令保持准确。

## 使用与文件入口

将整个 `awesome-docs/` 目录安装到目标工具支持的 skills 目录。只修改本仓库源码，不会自动同步其它位置的已安装副本。

- [SKILL.md](SKILL.md)：分类、路径、命名、维护与检查流程。
- [分类与输出结构](references/document-types.md)：目录、文件选择和短模板。
- [架构执行指南](references/architecture-writer.md)：L1–L4 每档的检查顺序、展开范围、图表和停止条件。
- [技术书执行指南](references/technical-book-writer.md)：章节依赖、符号管理、逐式推导、教学算例和修正步骤。
- [记录执行指南](references/record-workflows.md)：experiment、knowhow、reference、plan、roadmap、todo 的操作流程。
- [计划与报告模板](references/templates.md)：完成证据检查后使用的输出结构，不代替执行流程。
- [使用示例](references/examples.md)：分类边界、自定义路径、迁移和常用命令。
- [写后润色](references/post-write-polish.md)：按文档类型保护事实和术语。

## 维护时的检查

[功能案例](evals/evals.json) 覆盖限定粒度的架构、跨章符号冲突与高中水平推导、重复样本/缺失数据的实验及排障记录。另有独立使用、步骤重排、版本比较及局部润色的回归案例。案例是教学虚构数据；在临时目录生成文档，检查操作流程是否落实，测试产物不放进 skill 正文。每次改动仍需检查相对链接、示例算术和 skill 格式；单次 AI 检查不代表真实读者测试。
