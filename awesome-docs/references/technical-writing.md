# 技术写作：从读者问题到可核查的解释

用于新文档、较大改写、供应商说明及教学正文；适用于 Markdown、HTML 和讲解脚本。局部修改只执行相关检查。文档类型和展开深度仍由对应执行指南决定。

下面的工作记录留在临时笔记中，不作为额外交付物。交付正文不必套用这里的章节标题。先解决事实和阅读顺序，再润色句子。

## 使用顺序

- 写前：执行第 1–3 节，得到读者问题、证据和依赖顺序。
- 写中：执行第 4–5 节；操作说明用第 6 节，比较/查阅用第 7 节，计算解释用第 8 节。
- 写后：执行第 9–11 节中的适用检查。用户要求前后对比时，再用第 12 节。
- 架构边界、长篇推导和记录类型的专门流程，分别见 [architecture-writer.md](architecture-writer.md)、[technical-book-writer.md](technical-book-writer.md)、[record-workflows.md](record-workflows.md)。不在本页重复全部模板。

## 1. 把需求变成读者能回答的问题

**输入：** 用户请求、目标读者和已有材料。

1. 在笔记中补完一句话：“读者已经知道 __，读完要能 __，本文不展开 __。”信息可从上下文确定时直接采用；缺口会改变核心任务时再询问。
2. 把“介绍功能”“讲清算法”等宽泛目标，改成可回答的问题。例如：“输入是什么？”“在哪台主机发命令？”“收到哪个状态才算完成？”“这个数值怎样得到？”
3. 为每个核心问题指定正文位置。没有答案的位置标为待补证据；与任务无关的材料移出主线，不为已有材料硬凑章节。
4. 区分首次学习和随手查阅。前者补必要概念；后者把命令、范围或结论放到可直接找到的位置。

**检查与修正：** 用“读者能做什么”检查范围。若答案仍是“了解整体情况”，继续具体化；若一个问题需要另一类文档才能回答，链接到那里，不复制整篇。

示例：给接入工程师写任务接口说明，验收问题可以是“如何提交、如何判断完成、超时怎么办”。只写内部目录结构，未回答这 3 个问题。

## 2. 先分清事实，再统一术语

**输入：** 源码、协议、用户确认、历史文档或实验记录。

1. 给影响操作或结论的说法记录来源及适用版本。区分实现事实、实测、推导、假设、提案；不必给每个普通句子挂标签。
2. 对冲突材料保留各自范围，查清后再合并。示例值不等于默认值；某次成功不等于系统保证。
3. 抽取易混淆的对象和术语，记下“正文名称 ↔ 来源名称 ↔ 含义”。只有确认是同一对象才合并别名。主机、进程、线程和逻辑模块分别表述。
4. 将命令、字段、状态码、数值边界和责任主体列为改写保护项。自然语言别名可以解释，机器标识保留原拼写。
5. 找不到依据时，指出具体缺口及其影响。例如“现有协议没有说明重启后是否保留；持久化能力待确认”，不要补出保存命令。

**检查与修正：** 抽查关键句，能否指出依据并限定范围？若只来自图中的箭头、命名猜测或作者愿望，补证据或缩小结论。修正文案时不得把“可能”改成“会”，或把提案写成现状。

## 3. 按知识依赖排列正文

在笔记中为各节记录“回答什么 → 用到哪些已知信息 → 得到什么”。若某节用到后面才定义的概念，把最小必要解释前移；完整细节仍可后置。

| 读者任务 | 起草顺序 | 应优先暴露的问题 |
|---|---|---|
| 理解机制 | 要解决的问题 → 必要概念 → 输入及变化过程 → 结果和限制 | 公式从哪里来、为什么这一步成立 |
| 完成操作 | 目标及前提 → 操作 → 预期观察 → 异常分支 | 在哪里操作、何时停止或继续 |
| 查询接口 | 适用范围 → 输入输出契约 → 示例 → 错误和限制 | 字段、单位、边界、状态含义 |
| 比较版本/方案 | 比较对象与口径 → 同维度差异 → 对读者的影响 | 哪些变化需要修改调用或配置 |
| 理解架构 | 系统边界 → 运行单元 → 一条协作路径 → 状态及失败归属 | 谁执行、谁持有状态、何时交接 |
| 阅读实验 | 问题与样本 → 方法 → 结果 → 解释与不确定性 | 分母、筛选规则、比较条件 |

这是起草顺序，不是所有文档的固定目录。操作文档可把原理链接到后面；安全前提和影响操作的限制应留在操作前。

**检查与修正：** 从首节顺读，每遇到新术语、符号或对象，确认此前已解释，或确属读者已知。过渡句补“还缺什么才能继续”，不要只写“下面介绍下一部分”。

## 4. 让开头和标题直接帮助定位

依据 [Google 的文档组织建议](https://developers.google.com/tech-writing/one/documents) 和 [Microsoft 的可扫描内容指南](https://learn.microsoft.com/en-us/style-guide/scannable-content/)，先呈现当前读者最需要的信息，用可区分的标题组织细节。

1. 开头直接给出用途、关键答案或适用条件；删除只复述标题的导语。长背景放到确实需要它的地方。
2. 为每个标题写出本节的实际对象和问题。操作标题用动作，参考标题用稳定名称，解释标题指出关系。
3. 同级标题保持相近粒度；遇到“实现细节”中混放准备、操作和故障处理，按读者问题拆开。
4. 长文给可用的章节导航；改标题后检查锚点和已有链接，不靠显示标题猜链接仍有效。

| 定位困难 | 修改方向（本技能构造的示例） |
|---|---|
| 相关说明 | 支持的参数范围 |
| 结果处理 | 如何判断任务已完成 |
| 注意事项 | 超时后先查询任务状态 |
| 新旧对比 | 新旧协议的参数与返回状态差异 |

**检查与修正：** 暂时只看开头和目录，用第 1 节的问题寻找入口。某个核心答案只藏在“其它”中，就改标题或移动内容。无需机械消灭所有“概述”标题。

## 5. 逐段补全解释，逐句消除歧义

[Google 的段落指南](https://developers.google.com/tech-writing/one/paragraphs)强调段落主题和开头句。下面把它用于实际改稿；不设统一字数或句数配额。

1. 给一段内容概括一个中心意思。包含两个不同问题时拆段；同一解释被切成零碎短句时合并。
2. 检查首句是否引向这个中心意思。把主要结论或关系前移，但不把“先定义、再推导”的教学顺序强改为直接报答案。
3. 对关键动作圈出“谁、处理什么、在什么条件下、得到什么”。缺少且会产生歧义的项补齐；来源不明的责任主体先核实。
4. 对“因此、导致、随后、自动”等词检查依据：是因果、时序、触发条件，还是只观察到相关？把实际关系写出，不用连接词补造逻辑。
5. 将有多个可能指代的“它、该模块、这个结果”换成对象名；把埋在长句尾部的执行条件移到动作前。
6. 检查相邻段落：后段是否使用了前段没有得到的结果？若有，补缺失步骤或明确还需外部输入。

**构造示例，只有相应事实成立时采用：**

- 原句：“系统进行处理后自动完成闭环。”
- 已知事实：服务端受理命令；工作线程计算并写会话文件；归档由另一条件触发。
- 改写：“服务端受理命令后通知工作线程。工作线程完成计算，将结果写入会话文件。归档任务在满足触发条件后读取该文件；会话文件写入和归档完成是两个不同状态。”
- 仍需补充：若本文负责教读者判断归档完成，继续查明触发条件和完成标志，不能停在这段概述。

## 6. 把操作写成可以执行和判断的步骤

参考 [Microsoft 的步骤说明指南](https://learn.microsoft.com/en-us/style-guide/procedures-instructions/writing-step-by-step-instructions)：有顺序的操作用编号，在动作前说明必要位置，每步表达可执行动作。以下状态检查与失败处理是本技能的工程实践补充。

1. 提取前提、操作、观察结果、异常处理，不按原材料出现顺序照抄。
2. 将权限、工具位置、初始状态及有损操作警告放在相关动作之前。前提没有确认时，保留确认步骤。
3. 用“在何处，对什么做什么”起草步骤。连续的小动作可合并；出现等待、状态判断或分支时拆开。
4. 在容易误判的步骤后写预期观察及含义，分别识别受理、执行完成、检测通过和保存成功。
5. 把异常分支贴近触发它的步骤：看到什么 → 查什么/做什么 → 何时停止。只写有依据的重试或恢复方法。
6. 命令示例说明需替换的参数；保留原命令语法。记录命令不等于获准执行命令。

**构造例：** 已知 `START` 返回 `ACK` 表示受理，`STATUS` 返回 `DONE` 表示完成；超时后查状态，禁止自动重发；连接是前提。

- 差：“发送命令，成功后继续；注意要先连接。”
- 好：先建立连接；发送 `START`，收到 `ACK` 后等待；通过 `STATUS` 确认 `DONE` 后进入后续步骤。超时先查询状态，不重发 `START`。若协议未说明等待时限，标注该值待确认，不编造秒数。

**检查与修正：** 从初始状态桌面走读一次正常路径及已知异常路径。每一步都能判断下一步；若还要猜执行位置、成功标志或超时动作，回到对应步骤补齐。这只是文档走读，不能报告为设备实测。

## 7. 用相同口径写比较和参考资料

1. 先固定比较对象及版本；列出读者用于决策的维度，如范围、单位、命令、返回值、持久化和兼容性。
2. 每个维度同时填写各对象的事实和证据。区分“未知”“不支持”“不适用”，空白不自动解释为不支持。
3. 在相同单位、样本范围和前提下比较。条件不同就分别写清，避免把配置差异当成算法提升。
4. 把差异翻译成读者要做的事，例如“调用方需等待完成状态”，而非无依据的“更智能、更稳定”。
5. 可查阅内容采用字段/命令表；需要原因解释时另加短段落，不把操作契约埋在故事中。保留返回值示例和错误边界。

**检查与修正：** 任选读者会查询的一项，能否不读全文就找到对应版本的定义、范围和行为？若新版本有 5 个维度、旧版本只写“传统方式”，补齐同维度信息或明确资料缺口。

## 8. 把计算解释写到能复算

针对会影响结论或操作的指标，按实际依赖说明：

1. **取什么数据：** 对象、配对方式、样本集合及无效数据处理。图中高亮子集与实际计算集合分别说明。
2. **怎样变换：** 输入/输出坐标系、原点、方向、单位和必要标定条件。像素、物理位移、角度之间不直接混用。
3. **怎样计算：** 先定义量，再给关系和步骤；注明符号、绝对值、均值/最大值等聚合方式及运算顺序。
4. **怎样判断：** 阈值来源、作用在哪个统计量上、边界是否包含等号。未知阈值不由示例平均值擅自推出。
5. **怎样验证：** 代入一个标为构造或实测的算例，复算数值、单位和一个相关边界；给近似结果时注明近似条件。

**构造例：** 两个残差为 \(-2\) 和 \(2\)。\(\left|\frac{-2+2}{2}\right|=0\)，但 \(\frac{|-2|+|2|}{2}=2\)。只写“平均偏差”未定义这两者中的哪一个；应回到实现或规范确认，不由文案自行选择。

解释逆向计算时，检查已知量是否足够。总倾角不自动确定两个方向的投影角，还需要方向信息或额外约束。长推导使用 [technical-book-writer.md](technical-book-writer.md) 的符号与逐式推导流程。

## 9. 中文润色与公式格式

完成结构检查后，按下列顺序修改文字；详细事实保护规则见 [post-write-polish.md](post-write-polish.md)。

| 检查对象 | 修改动作 | 必须保留 |
|---|---|---|
| 空泛评价 | 删掉无证据的“全面提升”等；有事实就写具体变化 | 有来源的结论及其适用范围 |
| 动作被名词化 | “进行参数的读取操作”写成“读取参数”，必要时补执行者 | 执行对象及责任归属 |
| 重复预告 | 删去仅重复标题的“接下来我们将深入介绍” | 补足知识依赖的过渡 |
| 多种叫法 | 确认同一对象后统一正文称呼，首次出现给必要解释 | 命令、字段、别名映射及不同对象的区别 |
| 长句与指代 | 按条件/动作/结果拆分；消除不明确代词 | 否定、条件、数量、比较方向及不确定性 |

不靠禁用“不是……而是……”等句型去 AI 味；句子是否增加事实、解释或操作信息才是判断依据。不输出“AI 含量”分数。

中文排版参考 [中文技术文档指南的标点建议](https://zh-style-guide.readthedocs.io/zh-cn/latest/标点符号/中英文混用时标点符号用法.html)。中文叙述使用中文标点；代码、命令、网址和完整引文保留原语法。遵循项目已有空格和单位排版，局部改稿不顺带全篇重排。

本技能的交付约定：

- 数量、测量、范围、版本和百分比优先用阿拉伯数字，字幕同样适用；保留“三维”等自然术语及原始引文，不做全局数字替换。
- 数学式用 LaTeX，并在交付格式中渲染；图内标签、动态图示和正文一致。代码表达式留在代码格式中。
- 公式附近解释变量和单位，不只在远处附录定义。渲染后检查下标、负号、角度符号和换行，不能只确认源码含有 LaTeX。

## 10. 让图示承担明确的解释任务

先写一句“这张图帮助读者看清 __”。若只是重复标题，删除或重新设计。图示细节执行 [interactive-illustrations.md](interactive-illustrations.md)。

- 空间方向、投影和参考系关系优先考虑 3D；软件时序、变换步骤和数据流通常用 2D；同维度差异通常用表格。
- 指出图中每条重要连线代表什么：视线、变换、调用还是数据传递。过程图不要用无标注箭头替代条件和输出。
- 保留定位所需的背景对象。高亮当前参与计算的点、线、面；弱化不参与本步骤的对象，避免读者丢失原点、相机或所属参考系。
- 图注说明读者该观察什么及它支持哪一步结论。动画暂停、网页静态查看时仍应读懂关键关系。
- 分离视角旋转与模型参数变化；交互后高亮不丢失，数值不因相机视角改变。

## 11. 按缺陷修稿，不凭“更顺了”结束

| 实际检查 | 完成依据 | 发现问题后回到哪里 |
|---|---|---|
| 用读者问题查目录和开头 | 核心问题各有明确入口及答案 | 第 1、3、4 节：补答案或调整位置 |
| 顺读首用术语和符号 | 使用前/当处已解释，或确属读者已知 | 第 2、3、8 节：补定义和依赖 |
| 跟踪一条输入到结果 | 条件、执行者、输出和下一消费者可追踪 | 第 5、6 节：补中间步骤，不猜流程 |
| 对照关键结论与来源 | 版本、假设、未知项和实现范围一致 | 第 2、7 节：核实或收窄说法 |
| 复算例子与边界 | 数值、单位、聚合顺序、判定一致 | 第 8 节：修正方法或算例 |
| 看实际交付的图和公式 | 可读且与正文一致；相关交互确实测试 | 第 9、10 节及图示指南 |
| 润色前后核对保护项 | 数字、命令、条件、状态与责任未意外变化 | 恢复事实，再局部改写 |

优先修正影响读者操作和结论的缺陷，再处理措辞和版式。修完后重读受影响段落及相邻段，不为消灭所有“未知”扩大调查范围。

交付说明只报告实际完成的检查。静态链接检查、算例复算、渲染检查、模型走读、真人试读分别表述；未进行的检查保持未验证。正文已回答范围内的问题、路径可追踪、剩余缺口明确时停止。

## 12. 前后对照的边界

用户要求展示技能效果时，已有文档原样复制为基线，记录来源和哈希，不故意写差一版。任务、读者和代码版本保持可比；保留原有有用内容，区分组织、解释、措辞、图示及证据修正。

这是文档修订对照，不等于技能效果的受控实验。保存实际检查及限制，不伪称真人评测；未获要求不覆盖原项目文档。
